Core experience model

Two reading modes, one portfolio hierarchy.

Both modes carry the same content priorities. `Explore` guides the story. `Browse` compresses the same material into a faster dossier view.

Checkpoint 2 focus: approve the mode split and shared hierarchy before token decisions.
Explore

Guided narrative mode

  • Flagship case appears before the full work grid.
  • Motion supports entry, preview, and chapter pacing.
  • Stable message area keeps the story readable.
  • Reduced-motion fallback preserves the full hierarchy.
Browse

Dossier mode

  • Faster scan of grouped work and direct case-study links.
  • Minimal decorative motion and denser content packing.
  • Persistent access to flagship, proof, and experimental lanes.
  • Same visual language, different reading speed.

Case-study template

Story-led structure with proof anchored to each chapter.

The default pattern should work for most projects, with the dark technical mode reserved for archive-heavy or diagram-heavy cases.

01

Opening thesis

Product-level summary that clarifies the case before any gallery content.
02

Scope and role rail

Persistent orientation for role, scope, stack, and outcomes.
03

Problem framing

What needed to change, under what constraints, and for whom.
04

Key decisions

Main product, architecture, or UX choices and why they mattered.
05

Artifact chapters

Labeled visuals and system evidence grouped by decision relevance.
06

Outcome blocks

Ratings, scale, delivery, and operating proof beside the claims they support.
07

Reflection

Operating lessons and what the project demonstrates about capability.
Pattern rules

Each case opens with a thesis, not a tool list. The orientation rail persists. Artifacts need labels. Proof sits beside the chapter it validates. The dark technical mode is reserved for AI, platform, and system-heavy cases where diagrams need more room.

Persistent rail Labeled artifacts Proof beside claim Dark technical secondary
Proof distribution

Evidence should appear throughout the experience.

Instead of one isolated proof section, trust should be layered into the hero, flagship preview, case-study chapters, and enterprise or AI supporting stories.

Proof locations
H

Hero-level proof

Ratings, shipped scale, or role scope close to the thesis.
F

Flagship preview

Outcome and role proof directly beside the featured case.
C

Case-study chapters

Chapter-specific trust signals embedded where the claim is made.
E

Enterprise / AI support

Architecture, delivery complexity, and implementation scope highlighted in supporting lanes.
Preferred proof types
Ratings Shipped platforms Scale indicators Architecture scope Implementation depth Operational complexity

The site should support claims in real time. That means evidence appears where the user is reading, not only in a dedicated trust block later in the page.
